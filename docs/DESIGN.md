## 1. 它是什么、解决什么问题

### 1.1 问题

AstrBot 的一个会话就是一整条上下文。用户在同一个会话里从"帮我画个电路板"跳到"顺便看看 NAS
硬盘"时，模型会把两件事混在一起回答；上下文攒到 50 条被压缩后，话题边界彻底糊掉。

AstrBot 自身提供的是**手动**翻篇（`/new`）。问题是：用户不会记得手动翻，而且换话题的那一刻
用户自己往往也没意识到。

### 1.2 目标

在每条用户消息到达时，**低成本地**判断"这是延续还是新话题"，并根据配置采取不同强度的动作。

### 1.3 非目标

- **不做摘要、不改写历史**。判定只产出"延续/新话题 + 置信度 + 话题名"，动作交给模式配置。
- **不引入第三方依赖**。插件运行在宿主进程里，任何依赖都会变成用户的安装负担。
- **不删除任何对话**。`auto` 模式只新建对话，旧对话完整留档。

## 2. 设计哲学：三条铁律

### 2.1 误判代价不对称

这是全部设计的起点：

| 误判方向 | 后果 | 代价 |
| --- | --- | --- |
| 「新话题」误判成「延续」 | 上下文里混进旧话题，模型可能串味 | 小，可容忍 |
| 「延续」误判成「新话题」 | 用户正在聊的上下文被切走，**机器人在用户眼里失忆了** | 大，不可容忍 |

由此直接推出两个结论：

1. **默认模式必须是 `mark`**（只记录、不改上下文）；`auto` 要让用户观察几天后再自己开；
2. **判定层的合并规则必须偏向「延续」**（见 [3.4](#34-合并规则非对称)）。

### 2.2 失败即延续

模型超时、报错、返回的不是合法 JSON、上下文不可用、provider 配错……**一律按「延续」处理**。

理由：判定是**旁路增强**，不是主流程。旁路坏掉时，用户应该得到"和没装插件一样"的正常体验，
而不是"消息发不出去"。

工程后果：`_ask_llm()` 的所有异常分支都 `return None`；入口 handler 一律 `try/except` 兜住
（**而且必须兜住**，见 [5.2](#52-异常会连累同一条消息上的其它插件)）。

### 2.3 先观察，后行动

插件提供四种侵入性递增的模式，让用户自己决定何时"升级"：

| 模式 | 行为 | 侵入性 |
| --- | --- | --- |
| `off` | 完全不判定 | 无 |
| `mark`（默认） | 只写日志、维护状态，请求一个字不改 | 无 |
| `hint` | 往本轮注入一段**临时**提示（`mark_as_temp`，不进历史） | 低 |
| `auto` | 置信度达标时新建对话并切过去 | 高 |

## 3. 判定原理

判定分两层：**零成本启发式**（每条都跑）→ 不决时**问一次便宜模型**。

```
用户消息
   │
   ├─ 启发式（本地、免费、每条都跑）
   │    时间间隔 / 承接词 / 显式换话题词 / 消息长度 / 与会话内文字的相似度
   │
   ├─ 结论明确 ──────────────► 直接用（多数消息走这条，不花钱）
   │
   ├─ 拿不准 ──► 问一次便宜模型（默认跟随当前会话模型）
   │              把「当前话题 + 最近几条消息 + 机器人上一句回复」给它，要一个 JSON
   │
   └─ 模型超时/报错/输出不合法 ──► 一律当「延续」
```

### 3.1 相似度怎么算

三步，纯标准库：

```python
normalize(text):  去空白 → 转小写 → 去标点 → 数字折叠成 0
bigrams(text):    切成"连续两字"的集合   "电容选多大的" → {电容, 容选, 选多, 多大, 大的}
similarity(a, b): 两个集合的 Jaccard 相似度 = 交集 ÷ 并集
```

`compose_similarity()` 会把新消息与**话题名 / 话题摘要 / 上一条用户消息**各算一遍，**取最大值**。

> 为什么取最大值而不是平均：只跟话题名比会漏掉"同一件事换了个说法"；只跟上一条消息比又会被
> 「好的」「嗯」这类寒暄干扰。取最大值相当于"只要有任何一个参照物像，就算像"。

实测数值（真实语料）：

| 新消息 | 对比对象 | 相似度 |
| --- | --- | --- |
| 那这个电容选多大的？还有电阻呢 | 那这个电容选多大的？ | 0.615 |
| AstrBot 怎么装插件 | 怎么给 AstrBot 装插件 | 0.643 |
| 我没有代理啊 | 我没有代理 | 0.800 |
| 我没有代理啊 | 飞牛安装与AstrBot部署 | **0.000** |

### 3.2 启发式的九条优先级链

不是加权打分，而是**按顺序短路**——越靠前越"确定"，命中即返回：

| 顺序 | 条件 | 结论 | 调用模型 |
| --- | --- | --- | --- |
| 1 | 会话内还没有话题 | 建档 | 是（顺便让模型起名） |
| 2 | 距上条消息 ≥ `time_gap_minutes`(45) 且相似度 < `sim_continue` | 新话题 | 否 |
| 3 | 长度 < `min_message_length`(6) | 延续 | 否 |
| 4 | 命中显式换话题词（"换个话题""顺便问"…19 条） | 新话题（0.95） | 否 |
| 5 | 相似度 ≥ `sim_continue`(0.5) | 延续 | 否 |
| 6 | ≤12 字且含指代词（"它""那个"） | 延续 | 否 |
| 7 | ≤ `short_message_length`(25) 且无承接词 | **交模型判语义** | **是** |
| 8 | 相似度 ≤ `sim_new_topic`(0.12) 且无承接词 | 新话题 | 否 |
| 9 | 其余（模糊区间） | 交模型 | **是** |

三个设计细节：

- **承接词不是"命中就判延续"**，只作为第 8 条的否决条件（`and not marker`）——
  "还有呢？顺便问下硬盘"这种命令不该被"还有"挡住；
- **冷启动排在最前**：隔了 45 分钟再开口，即使只有「嗯」「在吗」两三个字也判新话题，
  不为了短句白问一次模型；
- **纯字符串匹配，没有分词**：词表就是 19 条换话题词 + 28 条承接词，够用且零依赖。

### 3.3 关键修正：不拿"字面不重叠"当证据

**背景**：v0.4.0 之前的启发式把"相似度 ≤ 0.12"直接当成新话题的铁证。用真实聊天记录评测后
发现这是错的。

**数据**（65 轮真实会话）：

```
启发式直接判「新话题」（不问模型）: 38 轮
其中「短消息（≤25 字）被判新话题」: 30 轮   ← 这些绝大多数是追问
相似度中位数: 0.000      相似度 ≤ 0.12 的轮次: 56/65 = 86%
```

被误判的例子：「我没有代理啊」「等等吧还没做完」「为啥直接闪退？」——它们与话题名的字符
相似度是 **0.00**，但都是**延续**。

**原因**：中文追问会彻底换词（"飞牛安装" → "我没有代理啊"），字符 2-gram 交集天然为 0。
**字面低相似在短句上几乎没有信息量。**

**修法**：短句不再由启发式定性，交给模型判语义。同一份数据的前后对比：

| 指标 | 旧 | 新 |
| --- | --- | --- |
| 判定为新话题的轮数 | 39 | 13 |
| 其中短句被误判 | 31 | 5 |
| 会去问模型的轮数 | 13 | 37 |

代价是模型调用变多（13 → 37 轮），换来的是"不再拿字面当证据"。可用
`short_message_length` 调小来收敛成本。

### 3.4 合并规则：非对称

`combine(heuristic, llm_verdict)` 刻意不对称：

| 启发式 | 模型 | 结果 |
| --- | --- | --- |
| 新话题 | 新话题 | 新话题，取两者**较低**置信度 |
| 延续 | 新话题，置信度 ≥ 0.8 | 新话题，置信度**压到 0.8** |
| 延续 | 新话题，置信度 < 0.8 | **延续**（保守） |
| 任意 | 延续 | 延续，置信度取模型与启发式的较大值 |

也就是说：**要让判定变成"新话题"，必须模型足够确定；要变成"延续"，任何一方说延续就够。**
这是 [2.1](#21-误判代价不对称) 的直接编码。

### 3.5 送进模型的提示词

```
当前话题：飞牛 NAS 安装
话题说明：在装飞牛系统，卡在格式化
最近几条用户消息（旧到新）：
- 格式化好慢啊
- 1T 的机械
机器人上一句回复：1T 机械盘那正常，慢慢等着吧
用户最新消息：那我现在咋退出去
请输出判定 JSON。
```

`机器人上一句回复` 是 v0.4.0 加的：很多换话题恰好发生在机器人回答之后（"好的，那再问个别的"），
模型看不到上一轮答了什么就没有承接关系的锚点。回复由 `on_llm_response` 钩子捕获、截断 1000 字
存进 `TopicState.last_assistant_text`。

模型被要求只输出一个 JSON：

```json
{"verdict":"continue"|"new_topic","confidence":0.0~1.0,
 "topic_name":"简短名称","topic_summary":"一句话说明","reason":"不超过30字"}
```

解析层（`parse_verdict`）对模型输出很宽容：剥 markdown 代码块、从噪声里抠第一个 `{...}`、
字段缺失就用启发式兜底。

## 4. 执行架构：两条路

### 4.1 为什么需要两条路

AstrBot 的消息处理器循环（`core/pipeline/process_stage/method/star_request.py`）：

```python
for handler in activated_handlers:
    if event.is_stopped():
        break          # 后面的处理器全部不执行
```

而注册表按优先级降序排序、**未声明优先级时默认 0**（`core/star/star_handler.py`）。

只要有**优先级高于本插件**的插件先跑并把事件静默掉（`event._force_stopped = True`），
排在后面的处理器就**一次都不会执行**。

> ⚠️ **v0.8.2 更正**：v0.8.0 曾把这件事归因于「消息防抖动插件（`priority=50`）先跑」。
> 那个归因**是错的**——`tests/reproduce_priority_race.py` 在真实注册表上验证过顺序，
> priority=50 的插件排在 priority=60 的本插件**之后**，没有机会先静默事件。
>
> 教训：只读取注册表里的 `priority` 字段值（旧版 §3.3 那种"隔离复现"）**验证不了真实
> 派发循环里的相对顺序**，必须把真实的 `StarRequestSubStage.process` 跑起来才算数。
>
> 因此优先级 60 只保证"比 50 高"，**不保证比所有插件都高**。真实环境若仍有入口零调用，
> 优先怀疑存在优先级 > 60 的第三方插件。实测表现：`hook_llm_request_v017` 触发 4 次、
> `handle_message_v017` 触发 **0 次**、`topic_state.json` 始终不存在。

### 4.2 两条路的分工

| 路 | 位置 | 优先级 | 能拿到 | 会被挡住吗 |
| --- | --- | --- | --- | --- |
| 消息事件 | `handle_message_v017` | **60** | 完整事件对象（`message_str`、`umo`） | 会（别的插件静默时） |
| 请求钩子 | `hook_llm_request_v017` | 60 | 只有 `ProviderRequest` | **不会**（不在循环里） |

两者都执行判定。请求钩子那条路**必须自己从提示词里抠用户消息**——这是本插件适配真实环境的
关键细节：

```python
marker = "用户最新消息："
tail = prompt.rsplit(marker, 1)[-1] if marker in prompt else ""
```

抠不出来（`prompt` 不是判定器那种格式）就安静跳过，不硬猜。这样即使别的插件在提示词里加了
自己的东西，也不会误判。

### 4.3 去重：两条路如何互不打架

两条路都可能先到、也可能都到，所以需要去重。**两路用不同的键**：

| 路 | 去重键 | 窗口 | 为什么 |
| --- | --- | --- | --- |
| 消息事件 | `消息ID\|时间戳`（存在 `state.last_detected`） | 永久（按会话） | 用户**重发同一句话**是新的消息 ID，必须算新一轮 |
| 请求钩子 | 文本归一化后前 120 字（存在 `RUNTIME.last_detect`） | **10 秒** | 只有钩子拿不到消息 ID；窗口短是为了不吞掉用户重发 |

钩子路还会把指纹落到 `TopicState.last_detected_hook`（**持久化**，v0.8.2 新增）。
修复前它判完只写内存里的 `RUNTIME.last_detect`，于是"钩子先判、事件路后到"时事件路
认不出来，同一条消息被判两次（`turns` +2）。

> ⚠️ **事件路绝不按文本拦**：它带平台消息 ID，是权威的消息身份，用户重发同一句话必须
> 算新一轮。v0.8.2 的第一版实现拿钩子指纹去拦事件路，把重发也吞掉了，被
> `tests/run_tests.py` 的 `[7]` 用例当场抓住。文本级跳过只对钩子路有意义。

> 第一版实现我用了"纯文本"当**两路共用**的键，结果**用户重发同一句话被误判成重复**——
> 被测试用例 `[7] 用户重发同样的话算新一轮` 当场抓出。这是个好例子：**去重键必须包含能
> 区分"同一条消息"与"同样的内容"的信息**。

### 4.4 handler 清单

| handler | 类型 | 优先级 | 职责 |
| --- | --- | --- | --- |
| `handle_message_v017` | `event_message_type(ALL)` | 60 | 判定主入口（路 A） |
| `hook_llm_request_v017` | `on_llm_request` | 60 | 判定备入口（路 B）+ `hint`/`auto` 请求改写 |
| `hook_llm_response_v018` | `on_llm_response` | 0 | 记录机器人回复，供下一次判定使用 |
| `command_topic_v017` | `command("topicweave")` | 60 | `/topicweave` 指令族 |
| `on_loaded_v017` | `on_astrbot_loaded` | 0 | 启动诊断（可用模型 ID、配置校验） |

**handler 全部是模块级函数**，不声明 `self`。原因见 [5.3](#53-handler-拿不到-self)。

### 4.5 模块布局

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `router.py` | ~1150 | handler、判定流程编排、指令、请求改写、诊断 |
| `detection.py` | ~451 | 启发式打分、提示词构造、结果解析与合并（**纯函数，易测**） |
| `state.py` | ~202 | 话题状态与持久化 |
| `main.py` / `__init__.py` | 9 | 入口，只做转出 |
| `_conf_schema.json` | — | WebUI 配置定义 |
| `metadata.yaml` | — | 插件元信息 |
| `build_zip.py` | ~188 | 打包器（含三道自检） |

**分层的用意**：所有判定逻辑都在 `detection.py` 的纯函数里（输入消息 + 状态，输出结论），
不和 AstrBot 的运行时耦合。所以能离线跑、能灌真实数据评测、能在任何 Python 3.10+ 上验证。

## 5. 六个实机踩坑

这一节是本文档最有价值的部分：每一条都是**线上事故换来的**，症状都有迷惑性。

### 5.1 消息入口被别的插件静默【严重】

**症状**：插件显示已加载、配置正确、日志里有活动记录，但聊天中**完全没有任何判定**：
没有日志、没有状态文件、没有提示，像没装一样。**群聊正常，私聊必现。**

**迷惑点**：`hook_llm_request_v017` 照常触发，日志"看起来很热闹"，让人误判为"插件在工作"。

**根因**：见 [4.1](#41-为什么需要两条路)。

**修法**（v0.8.0，双保险）：

1. 消息入口与命令声明 `priority=60`（高于 `astrbot_plugin_continuous_message` 的 50，
   见 `tests/reproduce_priority_race.py` 的顺序验证）。该处理器只判定与记录、
   不 `stop_event`、不发消息，提前执行不干扰别人的合并逻辑；
2. **判定迁移到请求钩子**——它不在处理器循环内，从机制上摆脱优先级比较。这一条更重要：
   优先级是相对值，今天高于 50、明天可能出现 100。

> **v0.8.2 更正**：上面第 1 条描述的"防抖插件先跑"并不成立（它排在 60 之后）。
> 但第 2 条的价值反而被这次排查**加强**了——真正能挡住入口的是优先级 > 60 的插件，
> 而**任何**优先级都无法提供绝对保证，只有"不在循环里"的钩子路径能。

### 5.2 异常会连累同一条消息上的其它插件

**症状**：插件自己出错，**别的插件也跟着不响应**。

**根因**：循环体是 `if event.is_stopped(): break`，而派发层在 handler 抛异常时会
`event.stop_event()` 并 break——**一个插件炸了，排在后面的全部跳过**。

**修法**：

- 入口 handler 一律 `try/except` 兜住所有异常；
- 判定层内部也各自兜底（`_ask_llm` 返回 None、`_apply_request_actions` 捕获告警）。

这条也解释了为什么早期"插件静静地什么都不做"那么难查：异常被自己的 `except` 吞掉，
日志里只剩一行 warning。

### 5.3 handler 拿不到 `self`

**症状**（实机日志）：

```
TypeError: TopicRouterPlugin.on_loaded_v017() missing 1 required positional argument: 'self'
```

**根因**：AstrBot 的调用是 `await handler.handler()`——**不传 `self`**。多数环境里注册表存的
是**绑定方法**（`self` 已绑定）所以没事；但至少有一个真实环境存的是**未绑定类函数**，于是：

| 签名 | 实际后果 |
| --- | --- |
| `(self)` | `missing 1 required positional argument: 'self'` |
| `(self, event, req)` | `missing 'req'`（event 落进了 self） |
| `(self, *args)` | 事件被塞进 `self`（日志里出现 `self=WebChatMessageEvent`） |

**修法**：所有 handler 改成**模块级函数**，签名 `(*args, **kwargs)`，用 `isinstance` 自己认参数：

```python
def _extract(*args, **kwargs) -> tuple[Any, Any]:
    """按类型/特征认出（事件, ProviderRequest），允许零参数。"""
    event = req = None
    for candidate in args:
        if isinstance(candidate, ProviderRequest):
            req = req or candidate
        elif event is None and _looks_like_event(candidate):
            event = candidate
    return event, req
```

状态与逻辑因此全部放在**模块级** `RUNTIME` / `_CTX` 上，方法体里不允许出现 `self.xxx`。

**这条约束对兼容性是净收益**：模块级函数没有 `self` 这个位置，AstrBot 怎么调都落对参数。
`tests/test_portability.py` 专门验证 7 种调用形态（绑定/未绑定/零参/只有请求…）。

### 5.4 handler 注册表按"模块名+函数名"复用

**症状**：改了代码、重装了插件、甚至重启了插件，跑的**还是旧版本**。日志里同时出现
"模块已导入 v0.5.1"和"hook_llm_request_v017 被调用 | v0.1.9"。

**根因**：`get_handler_or_create` 用 `f"{module_path}_{funcname}"` 当 key，**命中就复用旧元数据
与旧函数对象**。改代码不改函数名 → 热重载换不掉注册表里那条记录。

**修法**：handler 名字带版本后缀（`..._v017` / `..._v018`）。改判定逻辑而函数名不变时，
**必须重启进程**才能彻底生效——热重载不够。

> 这也是"改文件名没用"的原因：注册表认的是**函数对象**，不是文件内容。

### 5.5 指令名撞名

**症状**：AstrBot 面板提示"检测到指令冲突"，一条命令触发多个插件。

**根因**：冲突检测**实时读内存注册表**（`command_management._collect_descriptors`），
`topic`、`topicrouter` 这类通用英文词很容易和别的插件撞。

**修法**：指令名用不会撞的 `topicweave`，别名只留中文长名 `话题织机`。

**副产物认知**：热重载不会清理内存里的旧注册项，改名后必须重启进程才消失。

### 5.6 配错 `provider_id` 导致判定模型静默失效

**症状**：插件一切正常，但判定质量明显偏差（只有启发式在工作），日志里几乎看不出来。

**根因**：配置里写了不存在的模型 ID（例：`deepseek/deepseek-v4-flash`，而该环境实际是
`deepseek/deepseek-flash`）。`context.llm_generate()` 会抛 `ProviderNotFoundError`
（`core/star/context.py`），被"失败即延续"的兜底吞掉 → **模型层完全没跑**。

**修法**（v0.5.3）：

1. `_resolve_provider` 用 `provider_manager.get_provider_by_id()` 先校验存在性，配错就**告警
   并回退到当前会话模型**，不再静默失效；
2. 启动时比对"配置的 ID"与"可用列表"，不一致直接打 `⚠` 告警；
3. `provider_id` **默认值改为留空**（跟随当前会话模型）——原来硬写一个不保证存在的 ID，
   等于默认就错。

### 5.7 打包格式（附带）

**症状**：安装时报 `FileNotFoundError: .../plugin/astrbot_plugin_topic_router`。

**根因**：Windows 的"压缩文件夹"写**反斜杠条目名**且**不写目录条目**，Linux 上解包后
目录结构不对，AstrBot 收尾步骤 `os.listdir(<target>/<包名>)` 直接失败。

**修法**：只用 `build_zip.py` 打包（正斜杠 + 显式目录条目），并用上游真实的 zip 处理逻辑
做回归测试（`tests/verify_zip_install.py`）。

**顺带验证过**：上游的 `_resolve_archive_root_dir` 取"所有条目的公共前缀"，所以三种结构都能装：
插件目录当根、`仓库名-分支` 当根（GitHub Download ZIP）、文件直接放包根。

## 6. 数据模型与持久化

### 6.1 TopicState

每个会话（UMO）一条记录：

| 字段 | 含义 |
| --- | --- |
| `label` / `summary` | 当前话题名与说明（模型给的，或从消息截的） |
| `conv_id` | 当前对话 ID；变化时话题作废（用户 `/new` 了） |
| `last_user_text` | 上一条用户消息（相似度与承接词要用） |
| `last_assistant_text` | 机器人上一句回复（截断 1000 字） |
| `last_detected` | 消息级去重键 |
| `last_ts` | 上一条消息时间（冷启动判断） |
| `turns` / `switches` / `checks` | 轮数 / 换话题次数 / 本小时模型调用时间戳 |
| `disabled` | 本会话是否被 `/topicweave off` 关掉 |

### 6.2 持久化策略

`TopicStore` 写 `<数据目录>/plugin_data/astrbot_plugin_topic_router_pro/topic_state.json`。

两个设计点：

- **指纹比对跳过无意义写盘**：`_revision()` 算一份状态指纹（含 label/summary/conv_id/turns…），
  与上次落盘的指纹相同就不写；
- **失败不影响主流程**：读不到或格式坏掉就退化成空状态，不抛异常。

**状态只在 mark 模式下才有价值**——它是"先观察"阶段的观察记录，也是 `hint`/`auto` 的输入。

### 6.3 绕过 `ctx` 取状态

`_state()` 刻意不使用 `ctx`（只是保留签名对称），所以在请求钩子那条路（`ctx` 可能为 None）
也能工作。这是 [5.3](#53-handler-拿不到-self) 那种"不要依赖不确定的东西"思路的延续。

## 7. 配置项设计

设计原则：**每个旋钮都要能回答"什么时候该动它"**，否则不该做成配置项。

| 键 | 默认 | 什么时候动 |
| --- | --- | --- |
| `enabled` | true | 总开关 |
| `mode` | `mark` | 观察几天后改 `hint` 或 `auto` |
| `provider_id` | 空 | 想固定成更便宜的模型时填；留空=跟随当前会话 |
| `auto_threshold` | 0.8 | `auto` 误切太多 → 调高 |
| `min_new_topic_confidence` | 0.6 | 想更保守 → 调高 |
| `always_llm` | false | 只在英文等启发式失效场景考虑 |
| `sim_continue` | 0.5 | 判延续判太多 → 调低 |
| `sim_new_topic` | 0.12 | 判新话题判太多（长句）→ 调低 |
| `time_gap_minutes` | 45 | 群聊节奏不同 → 按实际调 |
| `min_message_length` | 6 | 太短的消息不值得判 |
| `short_message_length` | 25 | 想省模型调用 → 调小（0 = 恢复旧行为，不推荐） |
| `history_turns` | 3 | 判定不准且上下文长 → 调大 |
| `include_assistant_reply` | true | 想省 token 可关（不建议） |
| `detect_in_hook` | true | **别关**，见 [5.1](#51-消息入口被别的插件静默严重) |
| `timeout_seconds` | 8 | 模型慢 → 调大 |
| `max_checks_per_hour` | 30 | 话痨群控成本 |
| `new_conversation_notice` | true | `auto` 切换时是否提示 |
| `debug_log` | true | 排错时必须开 |
| `trace_enabled` | false | 要判断"入口到底有没有被派发"时打开（落盘取证，见 [8.0](#80-为什么需要-reproduce_priority_racepy)）|

**关于 `provider_id` 的教训**：默认值曾经硬写 `deepseek/deepseek-v4-flash`，而这是个**不保证
存在**的 ID，等于默认就配错。教训是：**插件的默认值不应该假设用户环境里有某个具体资源**。

## 8. 测试与评测体系

五套离线测试 + 一个评测台，共 **209 项断言**（150 + 16 + 9 + 21 + 13），全部不需要启动 AstrBot
（第一、三、四、五套要 import 真实的 AstrBot 代码）。

| 套件 | 项数 | 验证什么 | 需要 AstrBot 吗 |
| --- | --- | --- | --- |
| `tests/run_tests.py` | 150 | 插件逻辑、判定、状态、指令、跨路去重、落盘取证、边界 | 需要（解释器） |
| `tests/test_portability.py` | 16 | 7 种 handler 调用形态（用桩模块） | 不需要 |
| `tests/reproduce_hook_dispatch.py` | 9 | 注册表"同名复用"行为复现 | 需要 |
| `tests/verify_zip_install.py` | 21 | zip 安装流程（用上游真实代码） | 需要上游源码 |
| `tests/reproduce_priority_race.py` | 13 | **真实注册表 + 真实派发循环**里的优先级竞争 | 需要 |
| `tests/eval_topic_detection.py` | — | **真实数据评测台** | 不需要 |

### 8.0 为什么需要 `reproduce_priority_race.py`

前两套与"是否被调用"有关的测试都有盲区：

- `reproduce_hook_dispatch.py` 只验证"注册键按名字复用"；
- `run_tests.py` 的 `[7]` 用例是**直接调用** handler，绕过了派发循环。

于是"消息入口在真机上一次都没执行"这件事，在离线环境里**从来没有被真正复现或反驳过**——
这正是 v0.8.0 的错误根因能存活至今的原因。本套件补上这一环，用真实的
`StarRequestSubStage.process` + 真实的 `star_handlers_registry` 跑：

1. 注册表里各 handler 的 `priority` / `event_type` / `event_filters`；
2. 真实派发顺序（证明 priority 60 排在 50 之前）；
3. 事件被静默后循环 break、入口拿不到机会；
4. **同一事件下 `on_llm_request` 照常触发** —— 复现"只有钩子日志、没有入口日志"的形态；
5. 反向验证：**priority 70 才能挡住入口**（60 不是万能）；
6. `plugin.activated` 过滤路径（另一条被忽略的静默成因）。

### 8.1 真实数据评测台

这是本项目最有价值的基础设施。它直接读 AstrBot 的 `data_v4.db`，把**真实会话**灌进判定流水线：

```bash
python tests/eval_topic_detection.py                    # 纯启发式，零网络
python tests/eval_topic_detection.py --compare-legacy   # 旧 vs 新行为对比
python tests/eval_topic_detection.py --sim-new-topic 0.3 --gap-minutes 30
python tests/eval_topic_detection.py --json-out before.json
```

输出：混淆矩阵、精确率/召回率/F1、**模型调用占比**、判为"新话题"的置信度分布、误判样例。

**它直接催生了 [3.3](#33-关键修正不拿字面不重叠当证据) 的修正**——第一次运行就暴露了
"启发式直接判 38 轮新话题、模型一次没问，其中 30 轮是短句"。

**关于真值的诚实说明**：真实聊天记录里没有人工标注的话题边界，所以默认用**时间间隔代理**
（相邻消息间隔超过 `--gap-minutes` 记为新话题）。代理口径本身有噪声，**绝对值只当参考，
真正有用的是同一口径下的前后对比**。想更准可以用 `--labels` 传人工标注。

### 8.2 可移植性测试的设计

`test_portability.py` 用**桩模块**隔开 AstrBot 依赖，因此任意 Python 3.10+ 都能跑。它模拟
7 种调用形态，包括实机踩过的那些：

```python
for label, call_args in (
    ("零参数", ()),
    ("只传事件", (event,)),
    ("多传一个 self（未绑定调用的形态）", (SimpleNamespace(...), event)),
):
    ...
```

这是 [5.3](#53-handler-拿不到-self) 的回归防线：以后谁把 handler 改回类方法，这个测试立刻红。

## 9. 疑难排查案例集

真实排查历程，按"症状 → 定位手段"整理，可作为排查同类问题的参考。

### 9.1 "插件在跑但什么都不输出"

**排查顺序**：

1. 搜日志 `模块已导入` → 确认包是新的；
2. 搜 `handle_message_v017 被调用` → **没有**说明入口没执行（当时被误当成"代码坏了"）；
3. 检查 `topic_state.json` 是否存在 → 不存在说明判定流程从未进入；
4. 隔离复现：用宿主解释器单独 import 插件模块，打印注册表内容 → 确认 handler 全部注册成功；
5. **把真实派发循环跑起来**，查 `activated_handlers` 的实际顺序 → 别只看 `priority` 字段值，
   字段值相同/更大 ≠ 实际先执行；
6. **开启 `trace_enabled` 落盘取证** → 日志有级别限制、格式差异、还会把你自己敲的命令
   记进去造成假阳性，而落盘不受这些影响。

**结论**：代码没问题，是**执行顺序**问题。教训：**"插件加载成功"与"插件被执行"是两件事**，
日志里有活动记录也不能证明业务逻辑跑过。

> **v0.8.2 更正**：旧版这里写的"发现防抖插件 priority=50 且会静默事件"是**误判**——
> 那个插件实际排在本插件之后。真正的做法是第 5、6 步：跑真实循环 + 落盘取证。

### 9.2 "改了代码但行为没变"

**症状**：改了 `detection.py`、重装插件，判定结果一模一样。

**定位**：日志里同时出现两个版本号（"模块已导入 v0.5.1" + "被调用 | v0.1.9"）。

**结论**：注册表按"模块名+函数名"复用旧 handler，见 [5.4](#54-handler-注册表按模块名函数名复用)。
**必须重启进程**。

### 9.3 "判定质量明显不对"

**定位**：看判定日志里的 `source=` 字段——如果全是 `heuristic`、从不出现 `llm`，
说明模型层没参与；再搜 `判定模型调用失败`，就能看到 `Provider ... not found`。

**结论**：`provider_id` 配错，见 [5.6](#56-配错-provider_id-导致判定模型静默失效)。

### 9.4 排查手段清单（本项目积累的）

| 手段 | 用途 |
| --- | --- |
| `模块已导入 <版本> \| file=<路径>` | 确认加载的文件与版本 |
| `实例已构造 <版本>` | 确认插件类被实例化 |
| `imported.txt` 标记文件 | 日志被截断时的死证据 |
| handler 名字带版本后缀 | 区分"新代码注册的"与"旧注册表残留的" |
| 判定明细 `{heuristic, needs_llm, llm_used, has_reply, cost_ms}` | 一眼看出走了哪条路、有没有问模型 |
| `hook_... 被调用 \| has_event=... \| args=[...]` | 确认钩子拿到的真实参数形态 |
| `/topicweave conflicts` | 列出指令冲突（哪个指令被哪些插件注册） |

## 10. 开发规范与打包

### 10.1 改代码前必读

1. **handler 必须是模块级函数**，签名 `(*args, **kwargs)`，用 `_extract` 认参数；
2. **状态一律放模块级** `RUNTIME` / `_CTX`，**不允许 `self.xxx`**；
3. **入口 handler 必须吞掉所有异常**（否则连累其它插件）；
4. **判定失败即延续**——新增判定分支必须遵守；
5. **不要把"字面不重叠"当新话题证据**（短句交模型）；
6. **持久化数据写 `data/plugin_data/<插件名>/`**，不写插件目录；
7. 改了 `detection.py` **务必跑评测台**，用数据证明改动是变好还是变坏。

### 10.2 打包器与三道自检

```bash
python build_zip.py     # 输出到插件工作区的 dist/ 目录
```

**必须用它，不要用系统压缩工具**（见 [5.7](#57-打包格式附带)）。它包含三道打包前自检，
任何一道不过就拒绝打包：

| 自检 | 查什么 |
| --- | --- |
| `check_version_consistency()` | metadata / CHANGELOG / README 三处版本号一致 |
| `check_logo()` | PNG 有效性、1:1、256×256、体积 |
| `check_changelog_format()` | 首行标题、每个版本小节前后空行、版本号不重复 |

这三道自检都是**被实际错误逼出来的**：

- 版本号漂移过一次（CHANGELOG 写了新版、metadata 忘改，打出来的包名新、内容旧）；
- CHANGELOG 标题贴行过一次（Markdown 渲染成一坨）；
- logo 是发布到插件市场才补的，规格错了市场卡片会很难看。

### 10.3 版本号规则

`metadata.yaml` 的 `version` 必须带 `v` 前缀（如 `v0.8.0`），且与 `CHANGELOG.md` 顶部小节一致。
语义化版本：改架构/破坏兼容 → 次版本号（0.7 → 0.8）；改文档/打包 → 补丁号。
